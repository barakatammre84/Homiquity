## HIGH priority (new)

### H8 — MISMO export leaks full SSN + DOB to broker/lender external partners
- **Files:** `server/routes/lending.ts:859-894` (`GET /api/loan-applications/:id/mismo-export`) → `server/storage.ts:1804-1848` (`getMISMOLoanData`) → `server/mismo.ts:301-305, 544-552` (`generateMISMO34XML`)
- **Verified:** The route's `requireRole` explicitly includes `"broker", "lender"` (external partners, gated only by deal-team membership). `getMISMOLoanData` unconditionally calls `getDecryptedUrlaSsn` — a comment at `storage.ts:1816` claims "the export route restricts access... never a client," but a broker/lender *is* an external client, not internal staff. `generateMISMO34XML` writes full 9-digit SSN (`BorrowerSSNIdentifier`, `TaxpayerIdentifierValue`) and `BorrowerBirthDate` straight into the downloadable XML.
- **Why this matters:** This is the *same exposure class as H1*, on a second, independent endpoint — proves the redaction gap was systemic, not a one-off fixed by H1's patch. GLBA Safeguards Rule + Reg B minimization: MISMO/GSE delivery is an internal-staff action (brokers/lenders don't submit to DU/LP), so there's no legitimate reason for a partner role to hit this route at all.
- **Fix:** Restrict `requireRole` on the mismo-export route to internal staff roles only (simplest, and correct — this isn't a partner-facing action). If partner access is ever needed, strip `ssn`/`dateOfBirth` from the DTO before `generateMISMO34XML`, mirroring the H1 fix.
- **Priority:** Ship with the same urgency as H1 — identical regulatory exposure, currently live on `main`.

### H9 — In-progress work: S-06 rental-income offset is advisory-only, never reaches the binding decision
- **Files:** `server/services/preUnderwriting.ts:305-338` (uncommitted) vs `server/services/decisionEngine.ts:266-286`
- **Verified:** There are currently **uncommitted** working-tree changes (another session's WIP, not yet on `main`) adding a "Scenario 6" subject-property rental income offset (Fannie B3-3.1-08). `derivePreUnderwritingFlags` raises `SUBJECT_PROPERTY_RENTAL_OFFSET` with a computed `netOffset` and LO/borrower-facing copy like *"this adds $450/month toward your qualifying income."* But `decisionEngine.ts` builds `UnderwritingInput` from `aggregateBorrowerFinancials()` only — it never reads `preUwFlags` or `estimatedMarketRent`. The APPROVED/REJECTED/MANUAL_REVIEW decision and DTI never include this income. **This mirrors a pre-existing gap in S-05's `calculateRentalIncomeOffsets`** (not new), so it's a systemic pattern — but S-06 is new code about to be committed, so this is the moment to fix it before it ships the same bug twice.
- **Additional status notes on the same uncommitted diff (actionable before commit, not bugs in shipped code):**
  - No migration file exists for the new `urlaPropertyInfo.estimatedMarketRent` column (`shared/schema/lending.ts:765-768`) — `migrations/` stops at `0003_sms_opt_outs.sql`. Needs a targeted `ALTER TABLE` per the shared-dev-DB rule, not `db:push`.
  - `kb/UNDERWRITING_SCENARIOS.md` already marks S-06 `Status: Implemented`, but `scenarioCatalog.ts` has no `S-06` entry — **this will fail `tests/scenarioCatalog.test.ts`'s registry/catalog cross-check the moment this diff is committed.** It only passes right now because both files are uncommitted together.
- **Fix:** Either fold the rental net-offset into `aggregateBorrowerFinancials`'s income/debt totals (with PRELIMINARY-only provenance for self-reported market rent, consistent with the platform's provenance rules), or soften the flag copy so it doesn't imply the offset already changed the decision. Add the `S-06` entry to `scenarioCatalog.ts` and a migration file before merging.
- **Note:** Not yet in production — flagging so the owning session sees it before merge, not an incident.

## MEDIUM priority (new)

### M11 — DU submission gate ignores an undeclared/unscored co-applicant
`server/services/mismoValidation.ts:766-784` (`evaluateGseSubmissionReadiness`) blocks only on `gseGatingFailed` or `criticalErrors.length > 0`. `coApplicantLimitation` (set at `mismoValidation.ts:577-580` when a co-borrower is declared but has no URLA rows) is never checked by the gate — a joint application with a co-borrower entirely missing from the casefile can still pass DU submission. **Fix:** add `coApplicantLimitation !== null` as a third block condition, surfaced as its own field in the 422 body.

### M12 — `submit-gse` has no re-submission guard; repeat DU pulls are unmetered
`server/routes/aus.ts:133-267` never checks `ausSubmittedAt`/`ausCasefileId` before resubmitting. A retried request or trigger-happy LO can fire the same unchanged casefile at DU repeatedly — each one a billable AUS transaction and a write race on `ausFindings`. **Fix:** short-circuit to cached findings when recently submitted with no scored-field changes, or require an explicit `force: true`.

### M13 — Borrower-facing pipeline timeline renders "denied" as stage 0 (brand new)
`client/src/pages/lending/LoanPipeline.tsx:113-116` (`getStageIndex`) returns `0` for any status outside its local `STAGE_ORDER` list — which has no `denied` entry and no normalization map (unlike `StaffDashboard.tsx:276`'s `ComplianceChecklistInline`). A denied borrower checking status sees their progress bar reset to "Application," as if nothing happened. Same defect class as **M9 [carried over]** but a distinct, unguarded instance on the borrower-facing surface specifically. **Fix:** short-circuit to a "Application Denied" banner when `status === "denied"` instead of feeding it through the stage tracker.

### M14 — Auto-generated intake document requirements never notify the borrower
`server/pipelineEngine.ts:337-363` (`generateDocumentTasks`, called from `loanAnalysis.ts:476-477`) writes task rows with no accompanying email/notification — unlike the manual staff→borrower doc-request path (`borrower.ts:2688-2706`), which does notify. The borrower's *first* document ask is silent; they'd only discover it by logging in. This directly feeds **M2 [carried over]** (no reminder cadence) by making the earliest possible touchpoint invisible. **Fix:** send one consolidated "documents needed" notification/email after pipeline init, reusing the `document_requested` template.

### M15 — `/api/compliance/dashboard` re-runs the full MISMO validator per application, unbatched — and duplicates an existing batch helper
`server/routes/underwriting.ts:870-874` does `activeApps.map(app => getApplicationValidationSummary(app.id))` inside a `Promise.all`, each call independently scoring all 11 URLA sections, ATR/QM, HMDA, and TRID. This is a second N+1 in the same file as H7, on the same `StaffDashboard.tsx:430` mount. Notably, `getBatchValidationStatus` (`mismoValidation.ts:729-734`) **already exists and does this correctly** — the route just doesn't call it, and duplicates the loop inline instead. **Fix:** swap the inline `.map` for the existing `getBatchValidationStatus(activeApps.map(a => a.id))` — a trivial one-line change, not new work.

### M16 — VA zero-down advisory panel still assumes conventional PMI math in its live numbers
`client/src/pages/lending/PreApproval.tsx:294-326`: `estMortgage` hardcodes a PMI-inclusive tax/insurance factor regardless of `flags.vaZeroDown`, while the advisory copy a few lines below (337-343) correctly tells the veteran PMI is waived. The live DTI/payment number and the advisory text disagree for the same borrower on the same screen. **Fix:** branch `estMortgage`'s PMI assumption on `formValues.isVeteran && loanPurpose === "purchase"`, matching the copy's existing branch.

## LOW priority (new)

- **L8 — Stale task copy after H4 landed.** `taskEventEmitter.ts:354-358`'s `CMP_ADVERSE_ACTION` task still says "Generate adverse action notice," but H4 now auto-generates it synchronously before the status flips — the actually-outstanding action is **delivery** (`markAdverseActionDelivered`, uncalled except from `compliance.ts:952`, with no reminder). Confusing copy risks staff re-deriving or ignoring the real remaining 30-day obligation. **Fix:** retitle to "Deliver adverse action notice — confirm delivery within 30 days" and link `adverseActionId` into task metadata.
- **L9 — Generic in-app "status updated: denied" notification has no pointer to the adverse-action notice.** `lending.ts:1454-1463` fires the same generic body for every status change, including denial, ahead of the compliant email. Not an ECOA violation (the compliant notice exists in-account), but a missed, easy UX fix. **Fix:** neutral phrasing + direct link for the denied case.
- **L10 — No condo/HELOC/1099/trust-income document branches.** `pipelineEngine.ts:70-207` branches only on `employed`/`self_employed`/`retired` and LTV/credit thresholds; `propertyType === "condo"` is captured but never triggers a condo questionnaire/HOA-cert requirement, and 1099/trust-income borrowers fall into the generic W-2 employed bucket. **Fix:** add a `propertyType`-keyed branch and a `1099`/`trust_income` employment-type entry.
- **L11 — "My Queue" tab has no sort/filter controls.** `StaffDashboard.tsx:519-529` hardcodes SLA-then-time sort with no filter by task type/priority, unlike the Pipeline tab's search box. Friction for an LO managing 40+ tasks. **Fix:** add a lightweight filter bar, reusing the Pipeline search pattern.
- **L12 — Create Task's application picker has no search at platform scale.** `StaffDashboard.tsx:648-659` renders every application (up to the 500-row L3 backstop) as a flat `<Select>`. **Fix:** convert to a type-to-filter combobox.
- **L13 — No stale/failed indicator on the 30s pipeline poll.** `StaffDashboard.tsx:424-428` has no `onError`/`dataUpdatedAt` surfaced — a silently-failing poll leaves the LO staring at a stale snapshot with no visual cue. **Fix:** show "Updated Xs ago" / "Connection lost" near the refresh control.
- **L14 — Arbitrary `assignedToUserId` on task creation with no deal-team check.** `task-engine.ts:596` accepts any user ID system-wide; low severity (creates a task row, not a data leak) but an integrity gap. **Fix:** validate the assignee is deal-team/staff-scoped.
- **L15 — Retiree-specific copy compounds the known L1 issue instead of avoiding it.** `PreApproval.tsx:204-212, 494-500`'s `getDynamicTitle` actively asks "How many years have you been retired?" — reinforcing the question L1 already flags as unnecessary, rather than routing around it. Confirms L1's fix should also touch this copy branch.
- **L16 — Draft vs. coach-intake prefill precedence is silent and untested.** `PreApproval.tsx:842-900`: draft always wins over stale coach-intake data with no conflict surfacing or test asserting the precedence — deterministic today, easy to invert by accident later.
