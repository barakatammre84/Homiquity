## Prioritized backlog

### HIGH

**H10 — Binding decision engine consumes none of its own advisory scenario logic (S-01, S-03, S-04, S-05, S-06)**
- **Files:** `server/services/decisionEngine.ts:271-290` (builds `UnderwritingInput`) vs `server/services/preUnderwriting.ts` (all scenario logic) vs `server/underwritingEngine.ts:159-199` (`UnderwritingInput` type definition)
- **Verified directly this session:** `grep -n "preUwFlags\|PreUwFlag\|estimatedMarketRent\|netOffset" server/services/decisionEngine.ts server/underwritingEngine.ts` returns zero matches. `UnderwritingInput` at `decisionEngine.ts:271-290` is built purely from `fin.*` (raw `aggregateBorrowerFinancials` output), `app.*`, and `propertyInfo.occupancyType`/`numberOfUnits` — no field carries income-seasoning haircuts, verified-debt adjustments, significant-deposit flags, or rental-income offsets from any scenario.
- **What this means concretely:** `preUnderwriting.ts`'s `assessIncomeSeasoning` (S-01) can raise a `"blocking"`-severity `INCOME_SEASONING` flag on unseasoned income at the exact same time `decisionEngine.ts` counts that income at full face value in the binding APPROVED/REJECTED/MANUAL_REVIEW decision and DTI. Same pattern for S-03 (liability adjustment), S-04 (significant deposits), S-05 (rental offsets), S-06 (subject-property rental offset, just shipped). The scenario catalog (`scenarioCatalog.ts:38-165`) marks all six `status: "implemented"`, which overstates what's true — they're implemented as advisory conditions, not as decision inputs.
- **Why High, not Medium:** this is a correctness gap in the deterministic underwriting engine itself — the one piece of the codebase CLAUDE.md is most explicit about keeping trustworthy ("same inputs, same outcome"). Right now the *documented* inputs (raw financials) do produce a deterministic outcome, but that outcome can silently diverge from what the platform's own risk logic says is correct.
- **Fix:** Per the human-action item above — either (a) extend `aggregateBorrowerFinancials`/`UnderwritingInput` to fold in adjusted figures with explicit provenance tagging, or (b) leave the engine on raw figures by design and instead make `preUwFlags` severity `"blocking"` actually gate CTC via the conditions system (verify `checkPipelineProgress` truly enforces this — `preUnderwriting.ts`'s own doc comment says today it does not, conditions do, and the two aren't guaranteed to be in sync).
- **Acceptance criterion:** A test fixture with unseasoned income large enough to flip DTI over the policy threshold produces a different `decisionEngine` outcome than the same fixture with seasoned income — today it produces the identical outcome.

**H11 — ECOA §1002.9 adverse-action *delivery* timing has no tracking or enforcement**
- **Files:** `server/services/creditService.ts:1074-1117` (`ensureAdverseActionForDenial`, generation — correct), `creditService.ts:1119-1148` (`markAdverseActionDelivered`, delivery-marking), `server/routes/compliance.ts:940-975` (the only caller, manual staff-triggered)
- **Verified:** Notice *generation* is a solid chokepoint (denial is blocked if generation fails — H4, still fixed). But `deliveredAt` is only ever set by a human clicking a button; there is no scheduled job, deadline computation, or alert anywhere in the server tree for a notice that sits with `deliveredAt: null` past the ECOA 30-day window. A generated-but-undelivered notice is currently invisible to any dashboard or report.
- **Regulation:** ECOA / Reg B §1002.9(a)(1) — the 30-day clock is on notifying the applicant, not merely producing the document internally.
- **Fix:** Add a scheduled job (reuse the existing `jobs.ts` scheduler pattern) that flags any `adverseActions` row where `noticeDate` is more than N days old and `deliveredAt IS NULL`, surfaced on the compliance dashboard and/or as a staff task.
- **Acceptance criterion:** A denial with no delivery confirmation after the configured window produces a visible alert/task, not just a database row nobody queries.

**H12 — SLA-breach escalation is completely inert end-to-end (severity escalated from prior L2; new evidence found)**
- **Files:** `server/services/taskEngine.ts:371-409` (`executeEscalationActions` — all 4 action types are `console.log` only), `taskEngine.ts:564-574` (`runEscalationCheck` — has no scheduled trigger; only reachable via `POST /api/task-engine/run-escalation`, admin-only, manual)
- **Verified:** Grepped the full server tree for any cron/interval wiring of `runEscalationCheck` — none exists. Combined with the customer-success routine's separate finding that `sla_class_configs`/`task_type_sla_mapping` are empty tables in this environment (CS1, per memory), this means: even if someone manually calls the endpoint, the config that would define what counts as a breach doesn't exist, and even if it did, the "actions" taken on breach do nothing but log to console.
- **Why escalated from Low to High:** the 07-03 report filed this as "L2 — escalation actions are console.log stubs," which reads like a minor polish item. Tonight's check shows it's not just the action handlers — the entire trigger path is missing, meaning there is no live SLA enforcement mechanism in the product at all today, which is a bigger operational/compliance-adjacent gap than "logging instead of acting."
- **Fix:** Wire `runEscalationCheck` into the existing job scheduler; implement real `notify`/`reassign`/`freeze`/`alert` actions; populate `sla_class_configs` (cross-reference customer-success routine's CS1 ticket — this is the same root cause, two audits hitting it from different angles).
- **Acceptance criterion:** A task past its SLA threshold, with no manual intervention, produces a real notification/reassignment within one scheduler tick — verifiable via an integration test, not a manual curl.
