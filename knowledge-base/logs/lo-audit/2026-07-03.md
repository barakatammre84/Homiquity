## Executive summary

The LO stack is architecturally sound — the anti-steering *mechanics* (no manual rate entry, consent gated to lock-not-view), the MISMO completeness validator, the SLA/task model, and the batched `/api/dashboard` query are all genuinely well built. The problems are **wiring gaps**: several strong safety systems exist but are never called on the live path (doc-quality gate, MISMO completeness gate), one disclosure **over-promises** what the pricing engine computes (a real Reg Z exposure), one endpoint **leaks full SSN/DOB** to external partners, and the primary LO dashboard **silently breaks for every non-admin staff role**. None require large rewrites; most are a few lines to connect an already-built component to the path that should use it.

**Headline count:** 7 High, 10 Medium, 7 Low.

## HIGH priority (compliance risk or broken core LO functionality)

### H1 — URLA endpoint leaks full SSN + DOB to external partners
- **File:** `server/routes/borrower.ts:362-376` (`GET /api/urla/:applicationId`)
- **Verified:** The handler calls `getLoanApplicationWithAccess` (correct deal-team check) then returns `{ application, ...urlaData }` verbatim. `getCompleteUrlaData` → `storage.getUrlaPersonalInfo` (`server/storage.ts:1338`) is a plain `select()` with no column exclusion, so `personalInfo.ssn` (full 11-char SSN, `shared/schema/lending.ts:371`) and `dateOfBirth` ship in plaintext JSON to **any** deal-team member — including `broker`/`lender` external partners, whose membership is a routine low-friction grant.
- **Inconsistency proof:** the codebase already redacts PII for external partners elsewhere — `server/routes/compliance.ts:1057` nulls `borrowerSSNLast4`/`borrowerDOB`, and `compliance.ts:264-267` strips `rawResponse`/`plaidAccessToken` for non-internal staff. The URLA route has no equivalent guard.
- **Fix:** In `borrower.ts`, when `user.role === "broker" || user.role === "lender"` (i.e. `!isInternalStaffRole(user.role)`), mask `ssn` to last-4 and omit `dateOfBirth` before `res.json`. Mirror the redaction pattern in `compliance.ts:1057`.
- **Compliance:** GLBA Safeguards Rule + Reg B minimization; unnecessary PII exposure to third parties.

### H2 — Anti-steering disclosure attests to a "no risky features" option the engine never computes
- **Files:** `server/consentGate.ts:49-61` (disclosure text) vs `server/services/pricingAdapter.ts:212-224` (`computeOffers` labeling)
- **Verified:** `ANTI_STEERING_TEMPLATE.fullText` (line 57) tells the borrower they were shown *"3. The loan with the lowest interest rate that has NO risky features — no negative amortization, no prepayment penalty, no balloon payment in the first 7 years, no demand feature…"*. But `computeOffers` only ever pushes two labels — `LOWEST_RATE` (line 215) and `LOWEST_PAYMENT` (line 221). There is **no** risk-feature evaluation, and `rateSheetProducts` (`shared/schema/lending.ts:1851+`) has no `prepaymentPenalty` / `balloonPayment` / `negativeAmortization` columns to evaluate from. The borrower acknowledges (checkbox gating rate-lock, `lending.ts:812-829`) that a third option was presented when the system cannot show it did.
- **Fix (pick one):**
  - (a) Narrow `consentGate.ts` disclosure text to claim only what is computed (lowest rate + lowest total cost) until the third leg exists — *fast, closes the exposure tonight*; or
  - (b) Add the three risk-feature boolean columns to `rateSheetProducts` and a `NO_RISKY_FEATURES` label path in `computeOffers` — *correct long-term fix*.
- **Compliance:** Reg Z, 12 C.F.R. §1026.36(e)(3) — the safe-harbor requires the loan originator to actually *present* the three options; a disclosure asserting it without the underlying computation is the exposure.

### H3 — `submit-gse` has no MISMO completeness gate; incomplete packages reach DU
- **File:** `server/routes/aus.ts:123-242` (`POST /api/underwrite/submit-gse`)
- **Verified:** The only pre-submission validation is `if (loanAmount <= 0 || purchasePrice <= 0)` (lines 166-170). It never calls `validateMISMOCompleteness` / `getApplicationValidationSummary` (`server/services/mismoValidation.ts`) and never checks `gseReady`. `submitToDU` (`server/services/ausSubmission.ts`) only consumes loanAmount/propertyValue/creditScore/dti + report IDs — so nothing verifies SSN, DOB, citizenship, address, employment, or borrower declarations (all GSE-gating per `mismoValidation.ts` §1a/4/5) before the casefile is built.
- **Failure:** An application missing SSN/DOB/declarations submits successfully and is only rejected downstream at Fannie, wasting a DU pull and confusing the LO.
- **Fix:** Before `submitToDU`, call `validateMISMOCompleteness(applicationId)`; if `!gseReady`, return `422` with `criticalErrors` + the missing-field list. The validator (`mismoValidation.ts`) is thorough and already built — this is a wiring gap, not new logic.

### H4 — Denial email is decoupled from the ECOA adverse-action pipeline; no 30-day timer exists
- **Files:** `server/routes/lending.ts:1410-1415` (soft email) · `server/services/creditService.ts` (`generateAdverseAction`) · `server/routes/compliance.ts:823` (formal, staff-only) · `server/services/taskEventEmitter.ts:343-349` (`CMP_ADVERSE_ACTION` task)
- **Verified:** On any staff `status = "denied"`, `lending.ts:1411` fires `application_denied` (`emailService.ts:243-272`) with **only** `{ borrowerName }` — no reason codes, no creditor identity/address, no ECOA right-to-reasons language, and no requirement that the formal adverse-action notice at `compliance.ts:823` was ever generated or delivered. The status change *is* audited generically (`logAudit("loan_application.status_changed")`, `lending.ts:1426`) — but there is **no** ECOA-specific adverse-action record required, linked, or dated. `taskEventEmitter.ts:343-349` creates a "Generate adverse action notice" task, but `taskEngine.createTaskFromEvent` sets no `dueDate`, and no code anywhere computes `denied_at + 30 days` or flags an overdue notice.
- **Fix:** (1) Gate direct `status = "denied"` transitions to require a linked, delivered `AdverseAction` record (or block the soft email as the sole borrower communication). (2) Set `dueDate = denialDate + 30 days` on the `CMP_ADVERSE_ACTION` task and add an "overdue undelivered adverse-action" pass to the daily `lifecycleEngine.ts` sweep (already cron-driven).
- **Compliance:** Reg B, 12 C.F.R. §1002.9(a)(1) — notification of action taken within 30 days of a completed application, with statement of specific reasons.

### H5 — Staff dashboard silently breaks for every non-admin LO role
- **File:** `client/src/pages/staff/StaffDashboard.tsx:401-414`
- **Verified:** Three queries are enabled on `isStaff` but hit admin-only servers:
  - `["/api/admin/applications"]` → `server/routes/admin.ts:29` `requireRole("admin")`
  - `["/api/admin/users"]` → `server/routes/admin.ts:39` `requireRole("admin")`
  - `["/api/task-engine/tasks/by-role", ownerRole]` → `server/routes/task-engine.ts:534-542` `if (userRole !== "admin") return 403`
  The default `queryFn` in `client/src/lib/queryClient.ts` throws on non-401 status, so for `lo`/`loa`/`processor`/`underwriter`/`closer` these error out and `applicationsData`/`usersData` (consumed downstream at lines 486, 506-507 for *all* staff) go empty. The applications list, users list, and role task queue are broken for the majority of staff users.
- **Fix:** Scope those three `enabled:` flags to `isAdmin`, and add role-scoped equivalents (`/api/applications/mine`, `/api/task-engine/tasks/by-role` opened to the requesting user's own role) so LOs get real data instead of a broken panel.

### H6 — Document-quality confidence gate is dead code on the upload path
- **File:** `server/services/documentConfidence.ts:16` (`recordExtractionConfidence`)
- **Verified:** This function computes per-doc-type `reviewThreshold` (0.85 tax returns, 0.90 government ID) and sets `humanReviewRequired` below threshold. Grep across `server/` shows it is **never called**. Both extraction paths — `documents.ts` `/extract-*` endpoints (lines 275-465) and the fire-and-forget auto-extract in `lending.ts:1141-1159` — instead inline `status: extractedData.confidence === "high" ? "verified" : "uploaded"`, keying off a raw extractor string with no tie to the threshold table. The `getPendingReviews()` human-review queue receives no live rows.
- **Failure:** A blurry tax return the extractor scores "high" is auto-marked `verified` and never surfaces for human review.
- **Fix:** Call `recordExtractionConfidence()` at all four extraction sites and make the `verified` transition depend on `!humanReviewRequired` rather than the raw string. **Respects the platform invariant** — this *strengthens* the human-review queue, it does not automate condition clearing.

### H7 — `/api/pipeline/queue` N+1, polled every 30s — the LO's primary daily screen
- **Files:** `server/routes/underwriting.ts:567-623` · `server/pipelineEngine.ts:612-620`
- **Verified:** `Promise.all(activeApps.map(app => getPipelineSummary(app.id)))`; each `getPipelineSummary` runs 4 serial awaited calls (`getLoanApplication`, `getLoanMilestones`, `getLoanConditionsByApplication`, `getUser`). For 50 active files that is 200 round-trips per fetch — and `StaffDashboard.tsx:419` polls it `refetchInterval: 30000`, so the cost repeats every 30s for every logged-in staff user.
- **Fix:** Rewrite as 4 batched `inArray` waves (applications, milestones, conditions, users), assembling summaries in memory by `applicationId` — the exact pattern the `/api/dashboard` endpoint in `server/routes/lending.ts` already uses (house style).

## MEDIUM priority

### M1 — Task over-generation floods the LO task views too **[known-platform]**
`STATE_OF_THE_PLATFORM.md §4.1` documents borrower-side over-generation ("56 pending tasks"). **New this audit:** confirmed it equally floods the LO-facing `TaskOperations.tsx`. Two non-deduplicated writers hit the same `tasks` table — `pipelineEngine.ts:272-303` `generateDocumentTasks` (one row per requirement, legacy `status:"pending"`) and `taskEventEmitter.ts` via `taskEngine.createTaskFromEvent` (new `status:"OPEN"`). `GET /api/tasks` (`task-engine.ts:97-118`) and `getTasksByOwnerRole` (`taskEngine.ts:432-469`) return both systems unfiltered with no dedup. **Fix:** consolidate to the single event-driven path, or dedup/collapse by `(applicationId, documentType)` before any UI surfaces it.

### M2 — No automated reminder cadence for outstanding doc requests or stalled applications
`server/routes/jobs.ts` + `notifications.ts` have zero reminder/nudge/cadence logic. The only cron job (`/api/jobs/lifecycle`, daily) runs `lifecycleEngine.runLifecycleSweep`, whose only doc pass is `sweepAgingDocuments` (`lifecycleEngine.ts:155-190`) — nudging on *already-uploaded* docs >25 days old (good, keep it). Nothing chases an **unfulfilled** document request or an application stalled in a stage. **Fix:** add a "stale outstanding condition" pass (condition outstanding + no linked doc >5 business days → one capped reminder) using the `document_request` tasks already created by `generateDocumentTasks`. Squarely automatable — reminders, not condition clearing.

### M3 — VA instant-decision leaks a raw exception string into the LO's `missingItems`
`server/services/decisionEngine.ts:192-204` builds `UnderwritingInput` without `householdFamilySize` or `homeSquareFootage`; `server/underwritingEngine.ts:136-141` throws `"CRITICAL VA PROTOCOL ERROR: …"` for any `VA`/veteran file when those are missing (always — grep shows no writers). `decisionEngine.ts:206-214` catches it and returns `NEEDS_MORE_INFO` with the raw thrown message as the sole `missingItems` entry. An LO on a veteran's file sees the raw error string instead of a clean field list. Matches the catalog's own `S-02 "engine_ready" not "implemented"` note. **Fix:** collect the two fields at intake, or translate this specific error into clean items ("Household size", "Property square footage").

### M4 — TRID Loan-Estimate issue timing is never persisted
`server/routes/underwriting.ts:658` → `generateLoanEstimate` (`server/services/loanEstimate.ts:292`) sets `dateIssued = new Date()` at request time and returns it; there is no `loanEstimates` table write, so every re-fetch recomputes `dateIssued`. There is no durable, immutable record of when the borrower was first issued an LE. **Fix:** persist LE generation with an immutable `issuedAt` set once (first generation). **Compliance:** Reg Z §1026.19(e) — the 3-business-day delivery window needs an auditable issue/delivery date.

### M5 — No single "ready for underwriting" signal on the per-application LO screen
`mismo-validation` / `submit-gse` are referenced in `client/src` only from `StaffDashboard.tsx` as a rolled-up platform-wide `complianceData.gseReady` count (lines 115/535/1248) fed by `/api/compliance/dashboard`. There is no per-application readiness badge on `LoanPipeline.tsx` and no button anywhere that calls `submit-gse`. An LO must infer readiness from the documents/conditions tabs. **Fix:** surface a per-application readiness score (reuse the H3 validator output) as a badge on `LoanPipeline.tsx`.

### M6 — No SSN/phone/employer normalization before completeness scoring or MISMO export
`mismoValidation.ts` `hasValue()` (lines 72-74) checks presence only; `scorePersonalInfo` (237-255) confirms `ssn` non-empty but not 9-digit/formatted. A free-text SSN like `"123-45-678"` (8 digits) or an employer name with stray characters passes completeness and reaches the MISMO export unguarded, risking AUS rejection instead of a clear LO-facing error. **Fix:** add format validators (SSN 9-digit, phone E.164/10-digit, trimmed employer) to the scorer and normalize at export.

### M7 — Document-request emails omit the "why" the in-app checklist already carries
`emailTemplates.documentRequested` (`emailService.ts:296-320`) sends only a doc-type name + generic boilerplate. The checklist API (`lending.ts:266-355`) already carries a real `instructions`/`documentInstructions` field per task (line 319) that the email never receives. Borrowers get sparser guidance by email than in-app → preventable re-uploads. **Fix:** thread `task.documentInstructions` into `sendNotificationEmail({type:"document_requested"})` and render an instructions block.

### M8 — Gift-fund / reserves conditions keyed off LTV, not actual down-payment source
`server/pipelineEngine.ts:138-163` triggers `gift_letter` / `reserves_proof` purely on `ltvRatio > 80` / `> 95`. There is no `downPaymentSource` / `giftFund` field in `BorrowerProfile` (`pipelineEngine.ts:26-37`) to branch on. Result: a borrower using gift funds at 75% LTV gets no gift-letter condition, and one at 85% LTV using 100% own savings gets a spurious one. (Self-employed branching, by contrast, is correctly gated on `profile.employmentType` — leave it.) **Fix:** add `downPaymentSource` to intake and branch the gift-letter requirement on it directly.

### M9 — Three inconsistent, hand-maintained pipeline-stage taxonomies
`LoanPipeline.tsx:103-111` (`application, pre_approval, processing, underwriting, conditional_approval, clear_to_close, funded`, no `doc_collection`) vs `StaffDashboard.tsx:170-178` (`pre_approved, doc_collection, …, conditional`) vs `pipelineEngine.ts`'s actual `application.status` switch (adds `draft, submitted, analyzing, closing, denied`). `LoanPipeline.tsx` `getStageIndex` returns `-1` → treated as index 0, so a file truly in `doc_collection` renders at the *first* stage, understating progress to the LO. **Fix:** centralize stage definitions in one shared module imported by both client screens and `pipelineEngine.ts`.

### M10 — Missing index on `loan_conditions.applicationId` / `.status`
`shared/schema/underwriting.ts:1509-1532` — `loanConditions` has no index block (compare `tasks` at 170-175, which indexes both). It is queried by `applicationId` in `getLoanConditionsByApplication` (called from `getPipelineSummary` per app in the H7 N+1, plus `document-checklist` and `action-items` at `lending.ts:378`) with no index backing (Postgres does not auto-index FK columns). **Fix:** add `index("idx_loan_conditions_application").on(applicationId)` and `index("idx_loan_conditions_status").on(status)`. Use a targeted `ALTER`, not `db:push` (shared dev DB).

## LOW priority

- **L1 — `employmentYears` never skipped for `retired`/`other`.** `preApprovalMachine.ts:111-132` `computeRoute` hardcodes it into every route; schema requires min 1 char (`shared/schema/lending.ts:757-766`). A retired borrower must invent a "years at job" figure. **Fix:** exclude the step when `employmentType ∈ {retired, other}`, same pattern as the `incomeSources` conditional injection.
- **L2 — Escalation actions are `console.log` stubs.** `taskEngine.ts:352-391` `executeEscalationActions` logs but does not notify/reassign/freeze/alert. SLA states + "Breached" tab are real and good (`taskEngine.ts:114-143`); the automation behind them is not. **Fix:** wire `notify`/`reassign` to the notifications + assignment paths.
- **L3 — `/api/pipeline/queue` and admin `/api/tasks` return full sets (500-row backstop, no pagination).** `underwriting.ts:572-573`, `task-engine.ts:105`. Not severe today; grows into a large per-poll payload. **Fix:** paginate or default to the LO's own assigned slice.
- **L4 — emailService console-fallback returns `true` for the adverse-action path.** `emailService.ts:82-121` returns success even when only console-logged **[known-platform §3.5]**. **New angle:** for `application_denied` specifically this means an ECOA notice can be reported "delivered" when nothing was sent. **Fix:** return a real delivery status the caller can gate `markAdverseActionDelivered` on.
- **L5 — HMDA action-taken code 1 ("loan originated") may never be set.** `lending.ts:1284-1288` intentionally does not map "approved" → code 1 (correct — that's a funding event), but no funding/closing path sets it either. **Fix:** confirm the closer/funding flow populates action-taken code 1; add if missing. **Compliance:** HMDA/Reg C LAR completeness.
- **L6 — `/objects/:objectPath` resolves ownership via `allDocs[0]`.** `documents.ts:73-99` takes the first record for a storage path; if two records ever shared a path, authorization is decided by sort order. Low likelihood given `verifyAndClaimObject` uniqueness (the recent IDOR hardening is otherwise solid and complete). **Fix:** add a regression test asserting one storage path ↔ one document record.
- **L7 — 3s polling on `/api/messages` reaches staff sessions.** `client/src/pages/borrower/Messages.tsx:340` (3s) / `:333` (5s); LOs land on the same messaging surface working a file. All LO-only polls (pipeline 30s, tasks 30s, notifications 15s) are reasonable. **Fix:** back off to 10-15s or gate the tight interval to an active conversation.

## Verified clean (do not touch)

- **Anti-steering mechanics:** no LO-facing endpoint creates/edits a loan option or rate — `createLoanOption` (`storage.ts:1057`) is called only by the automated generator (`loanAnalysis.ts:404`); `computeOffers` is a pure function with no LO override. Closes the obvious steering vector. (`lending.ts` offers endpoint returns rate/LLPA only — no comp figures leak.)
- **Consent gating scope:** `hasBorrowerConsent("anti_steering")` correctly gates *lock* not *view* (`lending.ts:812-829`) — viewing options pre-consent is intended.
- **Lookup determinism:** `lookupResolver.resolveMatrixValue` throws a loud `CRITICAL DECISIONING ERROR` on an out-of-range FICO (`lookupResolver.ts:322-326`) — it does **not** silently return NaN/zero. (This resolves an open question flagged during the scenario-engine pass: the worst case is a loud, auditable failure, not mis-pricing. Residual is only error-string UX, same class as M3.)
- **PII discipline on credit/verification routes:** `/credit/pull`, `/credit/summary`, `/verifications/*`, `/mismo-export` all combine role + deal-team + external-partner redaction correctly. (The URLA route H1 is the lone exception.)
- **MISMO completeness validator** (`mismoValidation.ts`) covers all 11 URLA sections, ATR/QM points-and-fees, HMDA LAR, TRID due dates with a real holiday calendar — comprehensive. Its only problem is not being *invoked* (H3) or *surfaced* (M5).
- **FCRA/SSN intake sequencing:** funnel collects no SSN (`preApprovalMachine.ts:22-24`); soft-pull consent appears only on the final step. Correct.
- **Funnel prefill/autosave** (`PreApproval.tsx:534-559, 634-738`) — layered, type-validated, well engineered.
